# GENIUSBOT-CLIENT requirements

Every requirement this specification owns, with the proof that closes it. Delivery state
and public evidence for each ID are recorded in [`status.json`](status.json); this file
defines what each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md),
the test contract in [`test-spec.md`](test-spec.md), and the work order in
[`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `GENIUSBOT-CLIENT-R001` | **One backend-adapter import seam.** Every desktop panel and the main cockpit window route all Graph OS access through the shared gateway client facade and the single `BackendAdapter` seam; no other module imports the underlying engine package directly. | A source-tree scan test asserts only the gateway-client facade and the backend-adapter module import the engine package. |
| `GENIUSBOT-CLIENT-R002.1` | **Typed registry-entry model and validator.** A typed `OperationRegistryEntry`/`OperationRegistry` model validates operation name, sha256 digest shape, and HTTP method, and `build_registry` refuses a malformed or duplicate entry when the installed generated operation registry is loaded. | Unit tests assert each malformed-entry case (empty operation, bad digest, unsupported method, missing field, duplicate operation, digest mismatch) raises `OperationRegistryError` and a valid registry builds and resolves lookups. |
| `GENIUSBOT-CLIENT-R002.2` | **Operation validated against the installed generated registry at the call site.** Before invoking a Graph OS operation, the gateway client wires the `.1` registry model into its pre-call path and rejects an unknown operation or a registry/digest mismatch before any network call, consistent with the ecosystem's shared Graph OS operation-client contract. | Unit tests assert an unknown or mismatched operation produces zero network effect and a typed `CLIENT_UNAVAILABLE`-equivalent result. |
| `GENIUSBOT-CLIENT-R002` | **Typed registry-entry model and validator (rollup of 1, 2).** Rollup requirement: delivered by its child rows; LANDED only once every child is. | Every child row is LANDED. |
| `GENIUSBOT-CLIENT-R003` | **Verified credential over TLS, bounded responses.** The gateway client refuses a malformed endpoint, refuses plaintext HTTP to a non-loopback host without explicit opt-in, resolves a TLS profile for the caller's verified credential, and caps every response body against a fixed size limit. | Endpoint-validation and bounded-body unit tests cover unsafe URLs, declared-oversize and streamed-oversize responses. |
| `GENIUSBOT-CLIENT-R004` | **Off-thread, non-blocking dispatch.** Every Graph OS or backend network call runs on a background thread pool and reports back to the UI only through typed signals; no blocking network or heavy-reasoning call executes on the Qt event-loop thread. | Characterization tests exercise the worker's started/finished/error/progress signal contract and confirm the main window remains responsive during a dispatched task. |
| `GENIUSBOT-CLIENT-R005` | **Fail-closed, typed errors.** Every gateway facade method that fails (timeout, disconnect, malformed envelope, or an exception from the underlying SDK) returns a typed error/offline result to its caller instead of letting an exception escape into the Qt event loop or reporting a false success. | Unit tests drive timeout, disconnect and exception paths and assert a typed `"result"`/`"error"` payload is returned, never an uncaught exception. |
| `GENIUSBOT-CLIENT-R006` | **No local approval authority.** A governed or mutating action (an `ActionPolicy` approval, or a tool call behind the authorization dialog) is never authorized by the desktop process itself; the operator's explicit decision is always forwarded to Graph OS's server-side approval endpoint, which performs the authoritative check. | Contract tests assert the approval/grant code path issues a request to the gateway's approval endpoint and that no local code path marks an action authorized without that round trip. |
| `GENIUSBOT-CLIENT-R007` | **Embedded terminal sandbox.** The cockpit hosts an interactive terminal (`xterm.js` inside a `QWebEngineView`, bridged over `QWebChannel` to a native PTY/conpty backing process) and starts its backing shell lazily, only on first navigation to the terminal view. | Instantiation tests confirm the terminal widget and its bridge construct correctly, and a view-switch test confirms the shell starts exactly once on first navigation to that view. |
| `GENIUSBOT-CLIENT-R008` | **Lazy, on-demand cockpit panel loading.** Every secondary cockpit view (graph explorer, telemetry, workflow builder, security policy, infrastructure, finance, service dashboard, fleet supervisor, usage/cost, extraction, temporal graph, ask-data, metrics, federated search, voice) is imported and instantiated only on first navigation to that view, shares one background worker, and the sidebar highlights exactly the active view. | A characterization test walks every view index, asserts each panel loads exactly once, the placeholder widget is replaced, and only the active sidebar button is styled active. |
| `GENIUSBOT-CLIENT-R009` | **Honest voice-dictation states.** The voice dictation panel distinguishes no capture device present, a recorder/permission failure, the backend route being unavailable, and a genuine transcription error, and renders each state distinctly rather than collapsing them into one generic message. | Unit tests cover each state (no device, each mapped recorder error, unavailable route, generic failure) and assert a distinct rendered message per case. |
| `GENIUSBOT-CLIENT-R010` | **Background tray residency.** A system-tray daemon keeps the cockpit resident with show/terminal/health-check/exit actions, and closing the main window minimizes it to the tray instead of exiting the process while the tray remains active. | Tray action and close-event tests assert each tray action triggers its bound window behavior and that closing the window with an active tray icon hides rather than exits. |
| `GENIUSBOT-CLIENT-R011` | **Dynamic specialist discovery and schema-driven execution deck.** On startup the cockpit asynchronously discovers available specialist agents from the Knowledge Graph via the gateway and renders one dynamically schema-driven control card per specialist, mapping its declared skills or capabilities to input fields, and executes each specialist off-thread through the shared backend seam. | Unit tests cover the discovery-to-deck population path and the control card's skill-list, comma-separated-capability, list-capability and no-capability fallback field generation. |
| `GENIUSBOT-CLIENT-R012.1` | **Typed packaging manifest model and validator.** A typed `PackagingManifest`/`PackagingTarget` model and `build_manifest` refuse an incomplete manifest: a missing required target (`console_entry_point`, `onefile_executable`, `windows_installer`, `linux_desktop_entry`), a target missing its build tool or output path, or a target whose version does not match the source tree's declared version. No build tool is invoked. | Unit tests cover a complete manifest and each refusal case (missing target, missing field, version mismatch, duplicate target name, empty source version). |
| `GENIUSBOT-CLIENT-R012.2` | **Cross-platform packaging and distribution.** The desktop client is distributed as an installable Python package exposing a `geniusbot` console entry point, a single-file bundled executable, a Windows installer, and a Linux desktop-entry/package definition, each built from the same versioned source tree and described by a `.1`-validated manifest. | A packaging build (PyInstaller onefile, Inno Setup compile, and the Linux desktop-entry/control file lint) completes against a tagged revision and the resulting entry point launches the cockpit window. |
| `GENIUSBOT-CLIENT-R012` | **Typed packaging manifest model and validator (rollup of 1, 2).** Rollup requirement: delivered by its child rows; LANDED only once every child is. | Every child row is LANDED. |
| `GENIUSBOT-CLIENT-R013` | **Generated design-token colors.** `geniusbot/qt/colors.py` is generated from a tracked token source; a tracked generator script and source file exist and regenerating produces no diff. Touches `geniusbot/qt/colors.py`. | Test `tests/test_design_tokens.py::test_colors_match_generated_output`; negative: A hand-edited color constant fails the test. |
| `GENIUSBOT-CLIENT-R014` | **Finance cockpit panel contract.** `FinanceCockpitPanel` in `geniusbot/qt/finance_cockpit.py` reaches Graph OS only through the gateway facade and renders an unavailable state when the route fails. Touches that file. | Test `tests/test_finance_cockpit.py::test_panel_unavailable_state`; negative: A raised gateway error never escapes the panel. |
| `GENIUSBOT-CLIENT-R015` | **Packaged `geniusbot-development` skill.** A skill at `geniusbot/skills/geniusbot-development/SKILL.md` carries the rapid-delivery contract, commands, and gates, in the shape of `agent-webui-development`. Touches that file and `pyproject.toml` package data. | Test `tests/test_development_skill.py::test_skill_packaged_and_valid`; negative: A skill without front matter fails the test. |
| `GENIUSBOT-CLIENT-R016` | **Spec and docs hooks in pre-commit.** `.pre-commit-config.yaml` adds the `pipelines` hooks `public-surface`, `ste-staged`, `ste-staleness-staged`, `spec-standard` and `check-public-specs`, with `[tool.pipelines_hooks.public_surface]` and `[tool.pipelines_hooks.ste]` in `pyproject.toml`. Touches both files. | Test `tests/test_precommit_hooks.py::test_required_pipelines_hook_ids_present`; negative: Removing one hook id fails the test. |
| `GENIUSBOT-CLIENT-R017` | **Docs layout parity.** `docs/` gains `architecture.md`, `apps.md`, `design-system.md`, `deployment.md`, `features.md`, `start.md`, `status.md` and `agents.md`, listed in `mkdocs.yml` nav. Touches `docs/` and `mkdocs.yml`. | Test `tests/test_docs_layout.py::test_nav_lists_every_page`; negative: A page missing from nav fails the test. |
| `GENIUSBOT-CLIENT-R018` | **AGENTS.md section parity.** `AGENTS.md` gains the sections "What this repository owns", "Commands", "Quality gates", "Development rules", "Documentation" and "Branching & isolation" in webui order. Touches `AGENTS.md`. | Test `tests/test_agents_md_sections.py::test_required_headings_present`; negative: A missing heading fails the test. |
| `GENIUSBOT-CLIENT-R019` | **Run harness surface is read-only and honest.** The geniusbot client must show a run's current plan, context use against budget, applied harness configuration, cost and termination reason. The client reads only graph-os operations. | Children GENIUSBOT-CLIENT-R019.1 to GENIUSBOT-CLIENT-R019.6. |
| `GENIUSBOT-CLIENT-R019.1` | **Run operation wiring.** Model: `GRAPHOS-OPS-R021.4.5` serves the summary; `.4` serves separately labelled aggregates; `.6` supplies registration. Behavior: The view must select one `run_id` through the existing client transport. Wiring: the production path in plan.md must reach this field. Refusal: Absent registration, timeout or denial must show unavailable without direct engine calls. | Evidence: planned `tests/test_run_view.py::test_run_read_uses_graphos_operations`. A selected run must render through the served operation and existing client. |
| `GENIUSBOT-CLIENT-R019.2` | **Applied configuration.** Model: `GRAPHOS-OPS-R021.4.5` projects the decision edge owned by `EG-ORCH-VOCAB-R009.9`. Behavior: The view must show the recorded configuration reference and available `context_policy`, `plan_scaffold` and `action_space`. Wiring: the production path in plan.md must reach this field. Refusal: Missing or inaccessible configuration must not use defaults or the latest configuration. | Evidence: planned `tests/test_run_view.py::test_harness_config_shown`. A committed configuration must retain its reference and values through the client. |
| `GENIUSBOT-CLIENT-R019.3` | **Context and cost.** Model: `GRAPHOS-OPS-R021.4.5` maps `.2`, `.3` and `.8` of `EG-ORCH-VOCAB-R009`. Behavior: The view must label peak tokens, budget tokens and per-run USD cost separately. Wiring: the production path in plan.md must reach this field. Refusal: Null values must show unavailable; zero-solved abstention must not render zero cost. | Evidence: planned `tests/test_run_view.py::test_context_and_cost_shown`. Measured zero must render as zero; aggregate cost must retain its solved-task label. |
| `GENIUSBOT-CLIENT-R019.4` | **Read-only current plan.** Model: `GRAPHOS-OPS-R021.4.5` defines the snapshot boundary; `AU-HARNESS-R014` still lacks the required public export. Behavior: The view must show only an available authorized snapshot from `runs.get.current_plan`. Wiring: the production path in plan.md must reach this field. Refusal: Expired, wrong-run, regressing or unavailable snapshots must reveal no items or edit controls. | Evidence: planned `tests/test_run_view.py::test_plan_read_only`. A fresh matching snapshot must preserve item order, revision and AU statuses. |
| `GENIUSBOT-CLIENT-R019.5` | **Distinct terminal reasons.** Model: `GRAPHOS-OPS-R021.4.5` maps `EG-ORCH-VOCAB-R009.1`. Behavior: The view must map each recorded terminal reason to a distinct label. Wiring: the production path in plan.md must reach this field. Refusal: Unknown or missing reasons must show unavailable; overflow and stuck must not collapse to generic failure. | Evidence: planned `tests/test_run_view.py::test_termination_reasons_distinct`. Each of final_answer, context_overflow, stuck, step_budget and error must have its own label. |
| `GENIUSBOT-CLIENT-R019.6` | **Served surface proof.** Model: `GRAPHOS-OPS-R021.4.6` supplies registration and generated-client parity. Behavior: The test must enter the production UI and observe all fields through the real client and served operation. Wiring: the production path in plan.md must reach this field. Refusal: Denied reads after success must clear prior protected values; the UI must stay responsive without fabricated data. | Evidence: planned `tests/test_run_view.py::test_run_surface_end_to_end`. A served fixture must render summary, configuration, context, cost and an available plan. |
