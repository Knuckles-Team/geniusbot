# GENIUSBOT-CLIENT-001 requirements

Every requirement this specification owns, with the proof that closes it. Delivery state
and public evidence for each ID are recorded in [`status.json`](status.json); this file
defines what each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md),
the test contract in [`test-spec.md`](test-spec.md), and the work order in
[`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `GENIUSBOT-CLIENT-R001` | **One backend-adapter import seam.** Every desktop panel and the main cockpit window route all Graph OS access through the shared gateway client facade and the single `BackendAdapter` seam; no other module imports the underlying engine package directly. | A source-tree scan test asserts only the gateway-client facade and the backend-adapter module import the engine package. |
| `GENIUSBOT-CLIENT-R002` | **Operation validated against the installed generated registry.** Before invoking a Graph OS operation, the client validates the requested operation against the installed generated operation registry and rejects an unknown operation or a registry/digest mismatch before any network call, consistent with the ecosystem's shared Graph OS operation-client contract. | Unit tests assert an unknown or mismatched operation produces zero network effect and a typed `CLIENT_UNAVAILABLE`-equivalent result. |
| `GENIUSBOT-CLIENT-R003` | **Verified credential over TLS, bounded responses.** The gateway client refuses a malformed endpoint, refuses plaintext HTTP to a non-loopback host without explicit opt-in, resolves a TLS profile for the caller's verified credential, and caps every response body against a fixed size limit. | Endpoint-validation and bounded-body unit tests cover unsafe URLs, declared-oversize and streamed-oversize responses. |
| `GENIUSBOT-CLIENT-R004` | **Off-thread, non-blocking dispatch.** Every Graph OS or backend network call runs on a background thread pool and reports back to the UI only through typed signals; no blocking network or heavy-reasoning call executes on the Qt event-loop thread. | Characterization tests exercise the worker's started/finished/error/progress signal contract and confirm the main window remains responsive during a dispatched task. |
| `GENIUSBOT-CLIENT-R005` | **Fail-closed, typed errors.** Every gateway facade method that fails (timeout, disconnect, malformed envelope, or an exception from the underlying SDK) returns a typed error/offline result to its caller instead of letting an exception escape into the Qt event loop or reporting a false success. | Unit tests drive timeout, disconnect and exception paths and assert a typed `"result"`/`"error"` payload is returned, never an uncaught exception. |
| `GENIUSBOT-CLIENT-R006` | **No local approval authority.** A governed or mutating action (an `ActionPolicy` approval, or a tool call behind the authorization dialog) is never authorized by the desktop process itself; the operator's explicit decision is always forwarded to Graph OS's server-side approval endpoint, which performs the authoritative check. | Contract tests assert the approval/grant code path issues a request to the gateway's approval endpoint and that no local code path marks an action authorized without that round trip. |
| `GENIUSBOT-CLIENT-R007` | **Embedded terminal sandbox.** The cockpit hosts an interactive terminal (`xterm.js` inside a `QWebEngineView`, bridged over `QWebChannel` to a native PTY/conpty backing process) and starts its backing shell lazily, only on first navigation to the terminal view. | Instantiation tests confirm the terminal widget and its bridge construct correctly, and a view-switch test confirms the shell starts exactly once on first navigation to that view. |
| `GENIUSBOT-CLIENT-R008` | **Lazy, on-demand cockpit panel loading.** Every secondary cockpit view (graph explorer, telemetry, workflow builder, security policy, infrastructure, finance, service dashboard, fleet supervisor, usage/cost, extraction, temporal graph, ask-data, metrics, federated search, voice) is imported and instantiated only on first navigation to that view, shares one background worker, and the sidebar highlights exactly the active view. | A characterization test walks every view index, asserts each panel loads exactly once, the placeholder widget is replaced, and only the active sidebar button is styled active. |
| `GENIUSBOT-CLIENT-R009` | **Honest voice-dictation states.** The voice dictation panel distinguishes no capture device present, a recorder/permission failure, the backend route being unavailable, and a genuine transcription error, and renders each state distinctly rather than collapsing them into one generic message. | Unit tests cover each state (no device, each mapped recorder error, unavailable route, generic failure) and assert a distinct rendered message per case. |
| `GENIUSBOT-CLIENT-R010` | **Background tray residency.** A system-tray daemon keeps the cockpit resident with show/terminal/health-check/exit actions, and closing the main window minimizes it to the tray instead of exiting the process while the tray remains active. | Tray action and close-event tests assert each tray action triggers its bound window behavior and that closing the window with an active tray icon hides rather than exits. |
| `GENIUSBOT-CLIENT-R011` | **Dynamic specialist discovery and schema-driven execution deck.** On startup the cockpit asynchronously discovers available specialist agents from the Knowledge Graph via the gateway and renders one dynamically schema-driven control card per specialist, mapping its declared skills or capabilities to input fields, and executes each specialist off-thread through the shared backend seam. | Unit tests cover the discovery-to-deck population path and the control card's skill-list, comma-separated-capability, list-capability and no-capability fallback field generation. |
| `GENIUSBOT-CLIENT-R012` | **Cross-platform packaging and distribution.** The desktop client is distributed as an installable Python package exposing a `geniusbot` console entry point, a single-file bundled executable, a Windows installer, and a Linux desktop-entry/package definition, each built from the same versioned source tree. | A packaging build (PyInstaller onefile, Inno Setup compile, and the Linux desktop-entry/control file lint) completes against a tagged revision and the resulting entry point launches the cockpit window. |
